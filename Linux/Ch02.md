# Chapter 2: Working with Permissions and Privileged Accounts 

> Source: *Practical Linux System Administration* by Kenneth Hess (O'Reilly, 2023) 

## 1. Chapter Overview 

- For sysadmins, the **CLI is home**. There are dozens of commands, each with dozens of options. You'll only use a handful, but you need to know how to find the options you need and how to use them. 
- The CLI is still in use some 50 years later, a testament to its power and usefulness. 
- This chapter covers: 
 - Working as a **regular user** and as the **root user** 
 - Setting and modifying **file permissions** and understanding their effects 

--- 

## 2. Working as a Regular User 

- A Linux system has **two user types**: **regular users** and the **root (administrator) user**. 
- **Regular users:** 
 - Each gets their own **home directory**. 
 - Have almost unlimited power inside it (create, modify, remove, manipulate files) but almost none outside it. 
 - Can run many system commands. Others are restricted to users granted limited root access through **sudo**, or direct access to the root account. 
- The **root user** also has a home directory: `/root`. 
- **Security rule:** Always work as a **regular user** unless a task requires **privileged (root) access**. 

--- 

## 3. Working as the Root User 

- Root is the **all-powerful** account. It can create, edit, move, or remove any file, reboot, change runlevels, and shut down the system. 

**There are three ways to become root:** 

1. **Log in** as root 
2. Use the **`su`** (substitute user) command 
3. Use the **`sudo`** command 

### 3.1 Logging in as Root 

- Some distros allow direct root login over SSH or at the console. Others block SSH root login by default. 
- **Root login over SSH is not recommended** because attackers can try to **brute force** it. (The book later shows how to disable it.) 
- **Direct root login at the console is also discouraged**, because logging can't record who logged in and became root. 
- Recording who uses root matters because: 
 - When something goes wrong, you want to know which admin did what (not to lay blame) 
 - It satisfies some **regulatory requirements** 
 - It helps identify admins who need a "teachable moment" or more training 

### 3.2 Using `su` 

- `su` means **substitute user**. **Caveat:** the user must know the **root password**. 
- If admins know the root password, it's hard to stop them logging in as root directly. 
- Using `su` is acceptable only if **the root password changes after each use**. 
- In larger enterprises, security groups maintain root passwords and sysadmins **check them out temporarily** for maintenance. 
- **Root can `su` to any user without a password.** This is useful for troubleshooting, since users often can't describe problems accurately, and it spares the user from revealing their password to an admin. 

```bash 
[bjones@server1] $ su root 
Password: 
# 
``` 

- The `#` prompt means you're now **root**. Every command runs with root privilege and there are no restrictions, so **be careful**. 
- Book convention: **`$` = regular user**, **`#` = root**. 

**`su` vs. `su -`:** 

- The `-` means you also take on **root's full environment**, not just its privilege. 
- Running `env` after plain `su` shows the **original user's environment variables**, not root's. 
- `su -` is **equivalent to logging into the console as root**. 
- You don't need to type `root` because it's the default. 

```bash 
# exit # return to the original account 
[bjones@server1] $ su - 
Password: 
# env # now shows root's environment variables 
``` 

- Any user can `su` to any other user, but you need **that user's password**: 

```bash 
[bjones@server1] $ su cdavis 
Password: 
[cdavis@server1] $ 
``` 

### 3.3 Using `sudo` 

- The **best method** for root access. It stands for "**substitute user do**" or "**execute a command as another user**." 
- A properly configured account can issue **individual commands** as root. You must **precede each command with `sudo`**. 
- A **sudoer** is a user account configured for sudo use. 
- On first use, the sudoer supplies **their own password**. **Knowing the root password isn't required.** 

```bash 
$ sudo env 
[sudo] password for bjones: 
bjones is not in the sudoers file. This incident will be reported. 
``` 

- That warning means the user isn't configured in `/etc/sudoers`. 
- Pronunciation: sudo is "soodoo" and sudoer is "soodooer." The "soodoe" variants are also accepted. 

### 3.4 Creating a Sudoer 

- You need **root access** to edit `/etc/sudoers`. 
- Use the **`visudo`** utility, whose only purpose is editing that file. **Don't edit it directly with vi, Emacs, or any other editor.** 

```bash 
# visudo 
``` 

- `/etc/sudoers` is a simple text file describing users, groups, and commands that can run with root or other user privileges. 
- Configuration options: 
 - **Very restrictive**: run a single command as root. 
 - **Permissive**: run any command as root without a password. 
 - The author's preferred **mix**: sudoers can run any command as root but **must supply their own password**. 

``` 
## Allow root to run any commands anywhere 
root ALL=(ALL) ALL 
khess ALL=(ALL) ALL 
``` 

- Copy the root line and insert your username. The setting takes effect **immediately**. 
- **Setting up sudo without a password is not recommended.** Requiring a password and the `sudo` command itself makes admins **think about each action**, which leads to fewer mistakes as root.

## 4. Reading and Modifying Permissions 

- You must learn file permissions to set access to files and directories properly and to troubleshoot when users can't access something. 
- Permissions are simple but **central to Linux security**. Their simplicity makes them prone to neglect and misconfiguration. 
- **Common mistake:** Frustrated sysadmins loosen permissions to fix a problem and never restore the proper settings. 

### 4.1 Read, Write, Execute 

| Permission | Symbol | On a file | On a directory | 
|---|---|---|---| 
| **Read** | `r` | View the file | List directory contents | 
| **Write** | `w` | Create and modify the file | Copy, move, and create files in it | 
| **Execute** | `x` | Execute/run the file | `cd` into the directory | 

- On Windows, a `.exe` extension marks a file as executable. On Linux, a file is executable **based on its permissions**, not its name. 
- **Symbolic mode** uses the `rwx` designations. The other method is **numeric mode**. 

### 4.2 Numerical Permission Values 

| Permission mode | Numerical value | 
|---|---| 
| Read | **4** | 
| Write | **2** | 
| Execute | **1** | 
| None | **0** | 

- Values are additive and range from 0 to 7. 

### 4.3 Group Permissions (u / g / o / a) 

| Permission group | Symbol | 
|---|---| 
| User (owner) | `u` | 
| Group | `g` | 
| Other | `o` | 
| All (user + group + other) | `a` | 

- **All (`a`)** is shorthand for assigning permissions to every group at once. 
- You can set permissions for each group individually or all at the same time. 

### 4.4 Reading `ls -l` Output 

```bash 
$ touch file.txt # creates an empty file 
$ ls -l 
-rw-rw-r--. 1 khess khess 0 Jun 19 17:35 file.txt 
``` 

**Structure of the permission string:** 

``` 
- rw- rw- r-- 
│ │ │ │ 
│ │ │ └── permissions for other (o) 
│ │ └─────── permissions for group (g) 
│ └──────────── permissions for user (u) 
└──────────────── special character (file type) 
``` 

- **First position:** 
 - `-` = regular file 
 - `d` = directory (e.g., `dr-xr-xr-w`) 
- **Next nine positions** are three triads: **user, group, other**. 

**Numeric calculation (additive):** 

- `-rw-rw-r--`: user `rw-` = 4+2 = **6**, group = **6**, other `r--` = **4**, giving **664** 
- `rwx` = 4+2+1 = **7** 
- **750** = `-rwxr-x---`, so others have no permission. 
- The **other** group is often called **"world."** A file with `-rw-rw-r--` is **world readable**. 
- **Security note:** Giving others (the world) **write or execute** permission can be a security risk.

## 5. Changing File Permissions: `chmod` 

- `chmod` stands for **change mode**. 
- You can use **symbolic** (rwx and ugo) or **numeric** (0/1/2/4) designations, but you **can't combine the two** in one command. 
- The two methods are **equivalent**, and the author uses both interchangeably. 

### 5.1 Symbolic Mode 

**Operators:** `+` adds, `-` removes (subtracts). 

**Example 1: Remove read permission from others** 

```bash 
$ chmod o-r file.txt 
$ ls -l 
-rw-rw----. 1 khess khess 0 Jun 19 17:35 file.txt 
``` 

**Example 2: A script won't run ("Permission denied")** 

```bash 
$ touch file.sh 
$ echo "echo Hello" > file.sh 
$ ./file.sh 
-bash: ./file.sh: Permission denied 
$ ls -l 
-rw-rw-r--. 1 khess khess 11 Jun 29 19:58 file.sh 
``` 

- The `.sh` extension has no effect. The file **lacks execute permission**. 
- Fix: 

```bash 
$ chmod u+x file.sh 
$ ls -l 
-rwxrw-r--. 1 khess khess 11 Jun 29 19:58 file.sh 
$ ./file.sh 
Hello 
``` 

**Adding or subtracting multiple permissions in one command:** 

```bash 
$ chmod ug+x,o+w file.txt # add x for user and group, w for other 
-rwxrwxrw-. 

$ chmod a-x,o-rw file.txt # remove x from all, rw from other 
-rw-rw----. 

$ chmod a+x,o-r file.txt # add x for all, remove r from other 
-rwxrwx--x. 
``` 

> **Warning (default is all):** If you don't specify which group, the system assumes **all (`a`)**. This can be **dangerous** from a security perspective. 

```bash 
$ chmod +x file.txt # x granted to everyone (u, g, o) 
-rwxrwxr-x. 
``` 

> **Tip:** To run an executable file or script that isn't in your path, give an explicit path. If it's in the current directory, use `./script_name.sh`. 

### 5.2 Numeric Mode 

- In numeric mode there is **no adding or subtracting**. You simply **reassign** the permission value. 
- Example: the file's current value is **664** and you want **660** (remove read from others). 

```bash 
$ chmod 660 file.txt 
-rw-rw----. 
``` 

- The symbolic example above (`a+x,o-r`) in numeric form is **664 → 771**: 

```bash 
$ chmod 771 file.txt 
-rwxrwx--x. 
``` 

- Either method is fine. Changing permissions becomes automatic with practice and a few mistakes along the way. 

### 5.3 Symbolic vs. Numeric at a Glance 

| Goal | Symbolic | Numeric | 
|---|---|---| 
| Remove read from others (664 → 660) | `chmod o-r file.txt` | `chmod 660 file.txt` | 
| Add x for all and remove r from others | `chmod a+x,o-r file.txt` | `chmod 771 file.txt` | 
| Give the owner execute | `chmod u+x file.sh` | (reassign based on the current value) |

## 6. Default Permissions: `umask` 

- New files are created with **664 (`-rw-rw-r--`)** for a regular user. For **root**, the default is **644 (`-rw-r--r--`)**. 
- This happens because of the **umask (user file-creation mask)**, a global setting that **masks or filters** certain permissions from new files by default. 
- **Execute permission is never given by default**, so umask doesn't explicitly mask it. 

```bash 
$ umask 
0002 
``` 

- **Why four digits?** The leftmost digit is for **special permissions** (setuid, setgid, sticky), covered in a later chapter. Focus on the **rightmost three digits**: `002`. 
- Those three digits correspond to the rwx permissions for **user, group, and other**. 
- With `002`, **write (2)** is filtered out for other, so new files are `-rw-rw-r--`. 
- Root's default umask on the author's system is **0022**, which masks write for **both group and other**. 

**Why have a umask?** Security. 

- When a regular user creates a file, you don't want everyone else to be able to write to it. They must be granted that explicitly. 
- For root, the umask stops the root group and others from writing by default. This prevents **daemons or programs running as root** from writing to sensitive files such as `/etc/passwd`. Everyone may read it, but only root may write. 

**Changing umask temporarily (current session only):** 

```bash 
$ umask 006 
$ touch test.txt 
$ ls -l test.txt 
-rw-rw----. 1 khess khess 0 Jun 29 22:16 test.txt 
``` 

**Making it permanent (append to `~/.bashrc`):** 

```bash 
$ echo umask 006 >> ~/.bashrc 
$ source .bashrc 
$ umask 
0006 
``` 

- Every login now sets umask to **006 / 0006** (equivalent), giving a more secure default of `-rw-rw----`.
