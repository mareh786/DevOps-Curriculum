
# Chapter 4: Managing Users 

> Source: *Practical Linux System Administration* by Kenneth Hess (O'Reilly, 2023) 

## 1. Chapter Overview 

- Sysadmins spend a **significant portion of their time managing users**. They also troubleshoot user problems that aren't account- or permissions-related (connectivity, broken applications, data corruption, training issues, security issues, user-created problems). 
- **User management tasks:** 
 - Creating user accounts 
 - Modifying user accounts 
 - Removing user accounts 
 - Granting access to files and directories 
 - Restricting access to files and directories 
 - Enforcing security policies 
 - Setting permissions on files and directories 
- Some of this can be learned from the book. The rest is **experience and on-the-job training**. No two user environments are alike. 

--- 

## 2. User and Group ID Numbering Conventions 

These are **guidelines, not hard rules**, but they're followed on most corporate systems. 

| UID | GID | Description | 
|---|---|---| 
| 0 | 0 | Root | 
| 1–999 | 1–999 | System / service accounts | 
| 1000+ | 1000+ | User accounts | 

- User UIDs and GIDs typically **start at 1000** and increase by one per new account. 
- Root's UID and GID are **always 0**. No other user has these. 
- **System and service accounts** aren't human accounts and typically have **no interactive shell**. 
- Separating the ranges makes **housekeeping much easier** than random assignment.

## 3. Creating User Accounts 

There are two mainstream methods: **`useradd`** and **`adduser`**. 

### 3.1 Adding Users with `useradd` 

`useradd` is the standard command-line method. All you need is a username: 

```bash 
# useradd jsmith 
``` 

This: 

- Creates the home directory `/home/jsmith` 
- Fills it with the **default hidden environment files** (from `/etc/skel`) 
- Adds an entry to **`/etc/passwd`** 

**Adding the user's full name with `-c`** (writes to the fifth field of `/etc/passwd`): 

```bash 
# useradd -c "Jane Smith" jsmith 
``` 

**Adding more info** (separate with commas): 

```bash 
# useradd -c "Jane Smith,Room 26,212-555-1000,jsmith@example.com" jsmith 
``` 

Resulting entry: 

``` 
jsmith:x:1007:1007:Jane Smith,Room 26,212-555-1000,jsmith@example.com:/home/jsmith:/bin/bash 
``` 

### 3.2 Fields in an `/etc/passwd` Entry (left to right) 

| # | Field | 
|---|---| 
| 1 | Username | 
| 2 | `/etc/shadow` password field (`x`) | 
| 3 | User ID (UID) | 
| 4 | Primary group ID (GID) | 
| 5 | Comment field (GECOS) | 
| 6 | Home directory | 
| 7 | Default shell | 

### 3.3 Passwords and `/etc/shadow` 

- **Passwords are not stored in `/etc/passwd`.** The `x` points to `/etc/shadow`, which holds each user's **encrypted password**. 
- `/etc/shadow` is **readable only by root**. On Red Hat–based systems its permissions are `000`. They vary by distro but are **never readable by regular users**: 

``` 
----------. 1 root root 1547 Jul 17 10:55 /etc/shadow 
``` 

- A new account **can't log in** until it has a password. The shadow entry shows no password: 

``` 
jsmith:!!:18825:0:99999:7::: 
``` 

- Set an initial password with `passwd`, then give it to the user: 

```bash 
# passwd jsmith 
Changing password for user jsmith. 
New password: 
Retype new password: 
passwd: all authentication tokens updated successfully. 
``` 

### 3.4 Adding Users with `adduser` 

- On some distros, `adduser` is a **symbolic link to `useradd`**: 

``` 
lrwxrwxrwx. 1 root root 17 Oct 26 2020 /usr/sbin/adduser -> /usr/sbin/useradd 
``` 

- On others, `adduser` is an **interactive Perl script** that walks you through adding a user, and `useradd` is a separate utility with its own switches and arguments.

## 4. Modifying User Accounts 

- Accounts are rarely static. Use **`usermod`** to change things without editing `/etc/passwd`, home directories, or config files by hand. 
- **Common `usermod` changes:** 
 - Add the user to a supplementary group 
 - Change the comment field in `/etc/passwd` 
 - Change the home directory 
 - Set or remove an account expiry date 
 - Change the login name 
 - Lock or unlock an account 
 - Move the contents of the home directory 
 - Change the login shell 
 - Change the user ID 
- **Most frequently used:** change login shell, lock/unlock an account, set/remove expiry, add to a supplementary group. 
- **Rare:** changing a UID after creation or relocating a home directory. 
- Check the man page for other options. 

### 4.1 Adding a Supplementary Group 

- A new account gets a **UID** and a **primary GID** (they may match, but not always). 
- Example: Jane (UID/GID 1007) works in engineering and needs access to the engineering group's shared directory (GID 8020): 

```bash 
# usermod -a -G 8020 jsmith 
``` 

Resulting `/etc/group` entry: 

``` 
engineering:x:8020:bjones,kdoe,vkundra,adundee,jsmith 
``` 

- You can use the **GID number or the group name**: 

```bash 
# usermod -a -G finance jsmith 
``` 

- Add to **multiple groups at once**: 

```bash 
# usermod -a -G 8342,8901 jsmith 
``` 

> **Critical:** Always use **`-a` (append) together with `-G` (supplementary group)**. Without `-a`, the user is **removed from all other supplementary groups** and added only to the one you specify. 

### 4.2 Changing the User Comments (GECOS) Field 

- You can edit `/etc/passwd` directly, but that carries **significant risk**. 
- **Rule of thumb:** if there's a tool for the task, use it rather than editing config files directly. 
- Using `usermod -c`: 

```bash 
# usermod -c "Jane R Smith" jsmith 
``` 

- Using `chfn` (change finger information): 

```bash 
# chfn -f "Janie Smith" jsmith 
``` 

- *Finger* was an old daemon on early Unix and some Linux systems that supplied user information. It's rarely used now because of security issues, but the data is still called "finger information." 
- `chfn` options: `-f` full name, `-o` office, `-p` office phone, `-h` home phone. 
- Generally only the **full name** (or a service's name and purpose) is used in the GECOS field. 

### 4.3 Setting an Expiration (Expiry) Date 

- Useful when a user gives notice, moves business units, or goes on leave. Disable the account for security until they return or until you remove it. 

```bash 
# usermod -e 2021-07-23 rsmith 
``` 

- Date format: **YYYY-MM-DD**. `-e` sets the expiration. 

### 4.4 Changing a User's Login Shell 

- The default shell is **bash**, but users may request another. 
- **Three methods:** `usermod`, `chsh`, or editing `/etc/passwd` directly (**not recommended**). 

```bash 
# usermod -s /bin/sh jsmith 
``` 

Updated entry: 

``` 
jsmith:x:1007:1007:Janie Smith:/home/jsmith:/bin/sh 
``` 

- Only **root** can use `usermod` or edit `/etc/passwd`. **Any user can change their own shell with `chsh`:** 

```bash 
$ chsh -s /bin/zsh 
Changing shell for jsmith. 
Password: 
Shell changed. 
``` 

Resulting entry: 

``` 
jsmith:x:1007:1007:Janie Smith:/home/jsmith:/bin/zsh 
``` 

> **Tip:** The **"See Also"** section at the end of a man page lists related commands, links, and config files that may be more efficient. For `usermod`: `chfn(1)`, `chsh(1)`, `passwd(1)`, `crypt(3)`, `gpasswd(8)`, `groupadd(8)`, `groupdel(8)`, `groupmod(8)`, `login.defs(5)`, `useradd(8)`, `userdel(8)`.

## 5. Removing User Accounts 

Use **`userdel`**, which is as easy as `useradd`. 

```bash 
# userdel jsmith 
``` 

- Removes the user's entries from **`/etc/passwd`** and **`/etc/shadow`**. 
- **Leaves the home directory (`/home/jsmith`) intact.** 
 - Useful after someone leaves the company or changes roles. Only root can access any important documents they left behind. 

**Remove the home directory too (`-r`):** 

```bash 
# userdel -r jsmith 
``` 

- Appropriate if you make **nightly backups** of home directories and don't need to retain it. 

> **Warning:** Destructive commands such as `userdel` and `rm` are **irreversible**. Be sure you have the **correct account** before pressing Enter, and have **good backups**.

## 6. Forcing Password Changes 

- Relying on users to change their initial password is an "honor system" that **doesn't work 100% of the time**. 
- Audit account settings with **`chage -l`**: 

```bash 
# chage -l rsmith 
Last password change : Jul 17, 2021 
Password expires : never 
Password inactive : never 
Account expires : never 
Minimum number of days between password change : 0 
Maximum number of days between password change : 99999 
Number of days of warning before password expires : 7 
``` 

- Here the password **never expires**, which is a **security violation** to fix. 

**Force a change every 90 days, with a minimum of 1 day between changes:** 

```bash 
# chage -m 1 -M 90 rsmith 
``` 

| Option | Meaning | 
|---|---| 
| `-M 90` | Maximum days before a password change is forced | 
| `-m 1` | Minimum days between password changes | 

- **Why a minimum?** It stops users from changing their password repeatedly (until the system's remembered-password limit is exhausted) to get back to their original one, which amounts to **no net change**. 
- Expiration is **90 days after the last password change**. If the last change is further in the past, the user must change their password **at next login**. 
- Passwords are a **weak form of authentication** (they can be guessed, cracked, or written down), so make sure they're changed often and **not reused**.

## 7. Handling Service Accounts 

- Service accounts spark controversy, though every Linux system has **30+ of them**. Example, the `nobody` (Kernel Overflow User) account: 

``` 
nobody:x:65534:65534:Kernel Overflow User:/:/sbin/nologin 
``` 

**How to spot a service account:** 

- In `/etc/passwd`, the shell field is **`/sbin/nologin`**, meaning **no interactive shell and no password**. 
- Their passwords aren't blank or null; they **don't exist**. 
- **No one can log in** to them with any password. **Not even root** can `su` or `sudo` to them: 

```bash 
# su - nobody 
This account is currently not available. 
``` 

**Why it's not a security violation:** With no interactive shell and no way to switch to one via `su` or `sudo`, having service accounts is not a violation. The controversy comes from admins not knowing this. 

**Exception:** If a service **requires an interactive shell account**, apply **extreme scrutiny and extra security measures** to prevent clandestine logins on those accounts.

## 8. Managing Groups Rather Than Users 

Managing a **group** is more convenient than managing each user separately. 

**Group management lets you:** 

- Manage permissions on assets such as folders and files 
- Manage permissions by **job function** 
- Change permissions for **many users at once** 
- Easily add and remove users from a group's shared folders and files 
- Restrict permissions to sensitive folders and files 

**Why it matters:** Per-user permissions are hard to manage, since you'd have to trace them on **every system** where the user has an account. Group permissions allow **fine-grained access control at a more global level**. 

**Example:** A user moves from HR to Finance. Remove them from the HR group and add them to the Finance group. They **immediately** get access to Finance's shared files and lose access to HR's. 

### 8.1 Practice Scenario: Finance Shared Directory 

Assumes a `finance` group exists with users assigned. Users can change group ownership and permissions of files they own. 

```bash 
$ su - root 
Password: 
# mkdir /opt/finance # create the shared directory 
# chgrp finance /opt/finance # set group ownership to finance 
# chmod 770 /opt/finance # rwx for owner and group, none for others 
# exit # back to a regular account in the finance group 

$ cd /opt/finance 
$ touch budget.txt # created as -rw-rw-r-- khess khess 
$ chgrp finance budget.txt # file's group becomes finance 
$ chmod 660 budget.txt # -rw-rw---- (owner and group only) 
$ ls -la 
drwxrwx---. 2 root finance 24 Aug 11 21:58 . 
-rw-rw----. 1 khess finance 0 Aug 11 21:58 budget.txt 
``` 

**Steps explained:** 

| Step | Command | Effect | 
|---|---|---| 
| 1 | `mkdir /opt/finance` | Create the shared directory (as root) | 
| 2 | `chgrp finance /opt/finance` | Directory's group becomes `finance` | 
| 3 | `chmod 770 /opt/finance` | `drwxrwx---`: the group has full access, others none | 
| 4 | `touch budget.txt` | New file as a regular user in the group | 
| 5 | `chgrp finance budget.txt` | File's group becomes `finance` | 
| 6 | `chmod 660 budget.txt` | `-rw-rw----`: owner and group read/write, others none | 

> **Practice tip:** Add directories, create a group account, set group ownership on the directory, add users to the group, then `su - username` to **test permissions as that user**. If this example is clear, you're ready for the next chapter. If not, repeat it. These are **daily sysadmin tasks**.

## 9. Quick Revision 

| Topic | Key point | 
|---|---| 
| UID ranges | 0 = root, 1–999 = system/service, 1000+ = users | 
| Create user | `useradd -c "Full Name" username`, then `passwd username` | 
| `adduser` | Symlink to `useradd` on some distros, an interactive script on others | 
| `/etc/passwd` fields | username : x : UID : GID : comment : home : shell | 
| `/etc/shadow` | Encrypted passwords, root-only | 
| New account state | Shadow shows `!!`, so no login until a password is set | 
| Modify user | `usermod` (add group, comment, expiry, shell, lock/unlock) | 
| Supplementary group | `usermod -a -G group user` (**never forget `-a`**) | 
| Change comment | `usermod -c` or `chfn -f` | 
| Expire account | `usermod -e YYYY-MM-DD user` | 
| Change shell | `usermod -s` (root) or `chsh -s` (any user, own shell) | 
| Remove user | `userdel user` (keeps home) or `userdel -r user` (removes home) | 
| Audit passwords | `chage -l user` | 
| Force rotation | `chage -m 1 -M 90 user` | 
| Service accounts | Shell = `/sbin/nologin`, no password, safe by design | 
| Group management | Manage groups rather than individuals | 
| Shared directory | `mkdir`, `chgrp`, `chmod 770` |
